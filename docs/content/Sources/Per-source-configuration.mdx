# Per-Source Configuration

Every source in DocsGPT carries its own **behavior contract** — a small config object that controls how that source is *chunked* when it is ingested and how it is *retrieved* when you ask a question. This lets you tune each source independently: a large reference manual can use a different chunking strategy and retriever than a short FAQ.

You edit this config from a source's settings in the UI (shown below), or through the API. The same options are also available in **Advanced settings** when you first upload a document.

<Callout type="info" emoji="ℹ️">
Per-source retrieval is enabled by default. Operators can turn it off instance-wide with `PER_SOURCE_RETRIEVAL_ENABLED=false`, in which case all sources fall back to the classic retriever regardless of their stored config. Pre-screening and [relevance reranking](#relevance-reranking-and-the-decision-prescreen) then do not run either, and the decision model is never called for retrieval.
</Callout>

## Two kinds of settings: live vs. bake-time

The config has two groups of settings that differ in *when* they take effect:

| Group | When it applies | Re-ingest needed? |
| --- | --- | --- |
| **Retrieval** (`retrieval.*`) | Query time — applied live on the next question | No |
| **Chunking** (`chunking.*`) | Ingest time — baked into the stored chunks | **Yes** |

Changing a retrieval setting takes effect immediately. Changing a chunking setting only affects documents ingested *after* the change, so you must re-ingest the source to apply it to existing content. The API response includes a `requires_reingest` flag to make this explicit.

## Chunking configuration

Chunking decides how a document is split into the pieces that get embedded and stored.

```json
{
  "chunking": {
    "strategy": "classic_chunk",
    "max_tokens": 1250,
    "min_tokens": 150,
    "duplicate_headers": false
  }
}
```

| Field | Default | Description |
| --- | --- | --- |
| `strategy` | `classic_chunk` | Which chunking algorithm to use (see below). |
| `max_tokens` | `1250` | Upper bound on chunk size in tokens. |
| `min_tokens` | `150` | Lower bound; small fragments are merged up to this size. |
| `duplicate_headers` | `false` | Repeat section headers into each child chunk for context. |

### Available chunking strategies

| Strategy | Behavior |
| --- | --- |
| `classic_chunk` | The default token-window splitter. An empty config reproduces DocsGPT's historical chunking byte-for-byte. |
| `recursive` | Recursive character/token splitter that tries to break on natural boundaries (paragraphs, sentences). |
| `markdown` | Splits along Markdown structure (headings, sections) — good for docs and wikis. |
| `parent_child` | Embeds small **child** chunks for precise matching but carries a larger **parent** window in metadata, so the model still sees surrounding context. |
| `semantic` | Embeds sentences and splits where meaning shifts (at the 95th-percentile cosine-distance gap between adjacent sentences), falling back to `recursive` on failure. Produces topically coherent chunks at the cost of extra embedding calls during ingest. |

<Callout type="warning" emoji="⚠️">
Chunking is bake-time. After changing `strategy`, `max_tokens`, `min_tokens`, or `duplicate_headers`, re-ingest the source so existing chunks are rebuilt.
</Callout>

## Retrieval configuration

Retrieval decides which chunks are pulled in to answer a question. These settings apply live.

```json
{
  "retrieval": {
    "retriever": "classic",
    "exposure": "prefetch",
    "chunks": 6,
    "score_threshold": null,
    "rephrase_query": true,
    "prescreen": null,
    "reranker": null,
    "graph": {
      "seed_strategy": "entities",
      "passage_nodes": true,
      "blend_vector": true
    }
  }
}
```

| Field | Default | Description |
| --- | --- | --- |
| `retriever` | `classic` | Retrieval strategy: `classic`, `hybrid`, or `graphrag`. |
| `exposure` | `prefetch` | How retrieved context reaches the model: `prefetch` or `agentic_tool` (see below). |
| `chunks` | `6` | Final number of chunks (top-k) returned to the answer. Range 1–500. Set here, it **overrides** whatever a request asks for. |
| `score_threshold` | `null` | Minimum similarity score. Honored by pgvector, MongoDB Atlas, Qdrant and Milvus (MongoDB Atlas scores cosine as `(1 + cos) / 2`, so `0.8` there is cosine `0.6`; Qdrant's score follows `QDRANT_DISTANCE_FUNC`, cosine by default); FAISS, Elasticsearch and the `hybrid` retriever ignore it — the config API returns a `warnings` entry when you set it on one of those. |
| `rephrase_query` | `true` | Whether to run a query-rephrasing side-call before retrieval. |
| `prescreen` | `null` | Optional LLM relevance filter (see below). `null` = off. |
| `graph` | see [GraphRAG](/Sources/GraphRAG#graph-retrieval-settings) | How the `graphrag` retriever walks the graph: `seed_strategy`, `passage_nodes`, `blend_vector`. Ignored by the other retrievers. |
| `reranker` | `null` | This source's relevance reranking, within what the operator turned on: `null` follows the instance, `{"type": "off"}` opts out, `{"type": "decision", ...}` opts in. See [Relevance reranking](#relevance-reranking-and-the-decision-prescreen). |

### Who wins: source config or the request?

A source that has configured `retrieval.chunks` **outranks the value sent with a
request**. The owner tuned top-k for that corpus, so a client cannot raise or
lower it per call. Sources left at the default still let the request decide.

`chunks` is a total for the request, not a count per source: a request with
`chunks: 6` over three sources takes two chunks from each. Every attached source
still gets at least one chunk, so with more sources than `chunks` the answer
receives one chunk per source (eight sources at `chunks: 6` return eight
chunks). A source counts as configured when its stored
value differs from the default, so a source saved while the default was `2`
keeps `2` as its own setting.

Requests are also bounded: `chunks` is clamped to 0–500, and `0` still means
"skip retrieval for this turn".

### Retrievers

- **`classic`** — Vector similarity search. The default and a safe choice for any vector store.
- **`hybrid`** — Fuses vector search with full-text keyword search using Reciprocal Rank Fusion, which improves recall for exact terms, codes, and names that pure vector search can miss.
- **`graphrag`** — Knowledge-graph retrieval. Set indirectly when you enable GraphRAG on a source. See [GraphRAG](/Sources/GraphRAG).

<Callout type="warning" emoji="⚠️">
Keyword search for the **hybrid** retriever is currently implemented only for the **pgvector** vector store. On other stores (FAISS, Qdrant, Milvus, etc.) the keyword half returns nothing, so `hybrid` quietly behaves like `classic` (vector-only).
</Callout>

### Exposure: prefetch vs. agentic tool

`exposure` controls *how* a source's content is delivered to the model:

- **`prefetch`** (default) — DocsGPT retrieves the top chunks up front and injects them into the prompt before the model answers. Best for focused Q&A over a source.
- **`agentic_tool`** — The source is exposed to the model as a search tool it can call on demand, deciding when and what to look up (browse-as-you-go) rather than receiving a bulk prefetch. This is the default exposure for [Wiki sources](/Sources/Wiki-sources).

### Pre-screening (relevance filter)

Pre-screening adds an optional map-reduce step between retrieval and answering: a base retriever fetches a wider set of candidates, an LLM screens them in batches, and only the most relevant survivors are passed to the answer. It improves precision on noisy sources at the cost of extra query-time LLM calls, so it is **off by default**. Where the operator has turned it on, the [decision model](#relevance-reranking-and-the-decision-prescreen) can screen them instead, in one call.

```json
{
  "retrieval": {
    "chunks": 8,
    "prescreen": {
      "candidate_k": 40,
      "batch_size": 10,
      "max_keep": 8,
      "model": null
    }
  }
}
```

| Field | Default | Description |
| --- | --- | --- |
| `candidate_k` | `40` | Candidates fetched before screening. Must be `>= chunks`. |
| `batch_size` | `10` | Candidates screened per LLM call. |
| `max_keep` | `8` | Survivors kept after screening. Must be `<= candidate_k`. |
| `model` | `null` | Model used for screening. `null` reuses the request's resolved model. |
| `backend` | `llm` | `llm`, or `decision` to screen with the decision model while the operator has set `DECISION_PRESCREEN_ENABLED` (it runs as `llm` otherwise). Configs saved without it are `llm`. |
| `min_relevance` | `null` | `decision` only: chunks scoring below this relevance (0–1) are dropped. `null` uses `DECISION_PRESCREEN_THRESHOLD` (0.2). |

The screening judges the query retrieval searched with: on a follow-up turn, the standalone rephrase rather than the raw message.

## Relevance reranking and the decision prescreen

The [decision model](/Models/decision-model) can score each retrieved chunk with a calibrated relevance, `p(relevant)`: does the chunk contain information that answers the query or directly addresses it. Retrieval uses it in two ways:

- **Reranking.** A classic or hybrid source fetches 20 candidates instead of its usual top-k, orders them by relevance and keeps as many chunks as it would have without the model, most relevant first. It changes which chunks reach the answer and their order, not how many.
- **The decision prescreen.** A prescreen with `"backend": "decision"` scores all its candidates in one call instead of LLM batches, keeps those at or above `min_relevance` (always at least one), orders them by relevance and keeps at most `max_keep`.

On DocsGPT-shaped documentation (ten doc sites held out from the model's training, 1,314 queries, the top 20 of DocsGPT's default embedder graded by an LLM judge), reranking raised nDCG@10 from .758 in embedder order to .916, and the share of relevant chunks among the six kept from .377 to .473 at the same count. Those labels are one LLM judge's grades, the queries are standalone and mostly English, and the gain on finance Q&A, web pages or Spanish sources is smaller.

### The operator turns it on

A source cannot turn the model on: any user who can edit a source could otherwise make the API load a 1 GB model and spend CPU on it. Two settings in `.env` decide:

| Setting | Default | What it turns on |
| --- | --- | --- |
| `DECISION_RERANK_MODE` | `off` | The rerank for classic and hybrid sources (`DECISION_RERANK_RETRIEVERS`): `on`, `monitor` (scores and records without changing the result) or `auto` (on while the predicted call on this machine fits `DECISION_RERANK_BUDGET`, 3 s). |
| `DECISION_PRESCREEN_ENABLED` | `false` | `"backend": "decision"` prescreens on the model. The API loads the model when it starts, so the first call does not fail open while it loads. |

While `DECISION_RERANK_MODE` is not `off`, a source's `reranker` refines it:

```json
{ "retrieval": { "reranker": { "type": "decision", "min_relevance": 0.1, "candidate_k": 30 } } }
```

| Field | Default | Description |
| --- | --- | --- |
| `type` | `decision` | `decision` reranks this source in the instance's mode even where the instance default does not reach (a `graphrag` source, the rollout's control arm); under `monitor` it is only scored and recorded, since a source never raises the operator's mode. `off` opts it out, for example a source of one-line rows, which score low against any query. |
| `min_relevance` | `null` | Drop chunks scoring below this (0–1), keeping at least `DECISION_RELEVANCE_MIN_KEEP` (1). `null` uses `DECISION_RERANK_THRESHOLD` (0, reorder only). |
| `candidate_k` | `null` | Candidates fetched and scored, 1–100. `null` uses `DECISION_RERANK_CANDIDATE_K` (20). |

While `DECISION_RERANK_MODE` is `off`, every source is off, a stored `reranker` included. A group of sources searched together shares one candidate pool: an opted-out source is searched on its own, so its chunks are never judged by a policy it turned off. `DECISION_RERANK_ROLLOUT_PERCENT` applies the instance mode to a share of conversations, by a hash of the conversation id, so the two arms can be compared. Source settings show the reranker control only while `DECISION_RERANK_MODE` is not `off`, and the prescreen backend only while `DECISION_PRESCREEN_ENABLED` is set; a newly enabled prescreen then starts on the relevance model.

### On a CPU, `auto` keeps it off

By default the model runs in the API process on the CPU, where a rerank is slow. Measured with the release model on a 4-vCPU server (AMD Zen 4), reranking 20 whole chunks takes about 27 s. Where the model runs on a CPU, DocsGPT scores each chunk on its first 64 tokens plus the window that shares the most words with the query, `DECISION_RELEVANCE_CPU_PASSAGE_TOKENS` (256) tokens in all: about 14 s for 20 chunks and 7 s for 10 on that server, at recall@6 .812 against .853 for whole chunks. Both are far above the 3 s budget, so `auto` stays off on a CPU; on a GPU or an [API-mode](/Models/decision-model#api-mode) server, whole chunks are scored and `auto` turns it on where the call fits. If you set `on` for a CPU anyway, each call waits at most `DECISION_RELEVANCE_TIMEOUT` (2 s) and then keeps the retrieval's own selection.

### When the model cannot answer

Every failure keeps exactly what retrieval returns without the model: the same chunks in the same order. That covers the model being off, loading, busy or unreachable, a call past `DECISION_RELEVANCE_TIMEOUT`, and a batch answered only in part. A decision prescreen that fails keeps its first `max_keep` candidates, as the LLM prescreen does without a query.

### What else uses the scores

- Each kept chunk carries its `relevance` into the answer's sources. The sources panel and the citation reader label it as a strong (from 0.7), possible (from 0.3) or weak match, with the percentage in the tooltip; the embeddable widget does not show it yet.
- When the prompt has no room for every chunk, the least relevant one is dropped first, rather than the last.
- Sources searched in separate groups (different retrievers) are merged most relevant first when all of them were scored.
- The agent's search tool says "No relevant documents found" when a relevance threshold left none of the candidates, rather than "No documents found", so the agent can search again with other words.
- Workflow agent nodes are reordered under the instance rerank too, keeping every chunk.

### Where the text goes

The model runs in the API process or the stack's own decider by default, so chunks and queries stay inside the stack. In [API mode](/Models/decision-model#api-mode), every candidate chunk and the query are sent to the decision server you configured, the same trust boundary as an embeddings API: point `DECISION_BASE_URL` only at a server you trust with your sources' content. The decision record and traces keep numbers only.

## Testing retrieval

**Test retrieval** shows the chunks a query actually retrieves from one source, so you can tune the retrieval settings without asking questions in a chat. Open it from **Settings → Knowledge**, either with **Test retrieval** in a source's menu or with the **Test retrieval** button at the top of an open source. Anyone who can use the source can run it, including team viewers.

1. Type a query the source should answer.
2. Adjust the retrieval settings under the query if you want to try something else. They start from the source's saved settings.
3. Click **Run**.

The result lists the chunks in rank order with their file name, token count, score and text, plus the retriever used, the number of chunks and the latency. The settings you try are used for that test only and are **not saved**; change them in the source's settings to keep them.

The test runs the same retrieval pipeline as an answer: the same retriever, `chunks`, `score_threshold`, pre-screening and token budget. It differs in three ways:

- It never rephrases the query, as with the first message of a chat.
- It applies the source's settings even when `PER_SOURCE_RETRIEVAL_ENABLED=false`, where answers use the classic retriever. The operator's settings for the decision model still apply, but not `DECISION_RERANK_ROLLOUT_PERCENT`: a test has no conversation to put in an arm.
- Pre-screening without its own `model` uses the instance's default model, since a test has no chat model behind it. Settings that differ from the saved ones may use at most 20 pre-screening LLM calls (`candidate_k` / `batch_size`), a `decision` prescreen included while it runs on the LLM, and at most `DECISION_RELEVANCE_MAX_PASSAGES` (100) chunks scored by the decision model.

Where the operator has turned the decision model on, each chunk also shows its **relevance**, the summary says whether the model ordered the result, and **Compare with retriever order** lists every candidate in the order the retriever ranked it, with its relevance and what became of it: kept, promoted from past the retriever's own top-k, or dropped. With the rerank in `monitor` mode the result is the retriever's, and the comparison shows what the model would have changed.

### Reading the scores

The meaning of a score depends on the retriever and the vector store, and the modal labels each one:

| Label | Comes from | How to read it |
| --- | --- | --- |
| **similarity** | `classic` on pgvector, MongoDB Atlas, Qdrant or Milvus | Cosine similarity: higher is better, at most 1. This is the value `score_threshold` is compared with. |
| **distance** | `classic` on FAISS | L2 distance: lower is better, with no fixed upper bound. |
| **RRF** | `hybrid` | A reciprocal-rank-fusion score. It only orders the results of this query; don't compare it across queries or with a threshold. |
| **no score** | `graphrag`, and `classic` on Elasticsearch | The retriever ranks chunks without a comparable per-chunk score. A `graphrag` source that has no graph yet falls back to classic retrieval, so its results carry the vector store's scores instead. |

When nothing comes back and a `score_threshold` is set, the modal says so: lower the threshold to see the near misses.

### From the API

```bash
curl -X POST https://your-docsgpt/api/sources/<source_id>/search \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "How do I rotate the encryption key?",
    "retrieval": { "retriever": "hybrid", "chunks": 4 }
  }'
```

`query` is required (at most 2,000 characters). `retrieval` is optional: leave it out to use the source's saved retrieval settings, or send a complete retrieval object (fields you leave out take their defaults, as in the table above). `"compare": true` adds `candidates`. Nothing is saved. The response:

```json
{
  "success": true,
  "query": "How do I rotate the encryption key?",
  "retriever": "hybrid",
  "retrieval": { "retriever": "hybrid", "chunks": 4, "...": "..." },
  "total": 4,
  "latency_ms": 182,
  "chunks": [
    {
      "rank": 1,
      "text": "...",
      "title": "...",
      "filename": "security.md",
      "source": "...",
      "tokens": 212,
      "score": 0.0328,
      "score_kind": "rrf",
      "relevance": 0.91
    }
  ],
  "relevance": { "applied": true, "fallback": null, "latency_ms": 412 },
  "candidates": [
    { "rank_before": 1, "rank": null, "kept": false, "baseline": true, "relevance": 0.04, "text": "...", "...": "..." }
  ]
}
```

`score_kind` is `cosine_similarity`, `l2_distance`, `rrf` or `null`, matching the labels above; `score` is `null` when `score_kind` is. `relevance` on a chunk is the decision model's score when it ordered the result, else `null`. The top-level `relevance` is `null` when the model did not run; otherwise `applied` is `false` in `monitor` mode or after a failure, and `fallback` names the failure (`timeout`, `unavailable`, `error`). Each of `candidates` (with `compare` only) has its place in retriever order (`rank_before`), in the result (`rank`, `null` when not kept), whether it was kept and whether retrieval would have returned it without the model (`baseline`).

## Editing the config via API

The config is edited with a `PATCH` to the source's config endpoint:

```bash
curl -X PATCH https://your-docsgpt/api/sources/<source_id>/config \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "retrieval": { "retriever": "hybrid", "chunks": 4 },
    "chunking":  { "strategy": "semantic" }
  }'
```

The response echoes the stored config and a `requires_reingest` flag:

```json
{
  "success": true,
  "config": { "...": "..." },
  "requires_reingest": true
}
```

Notes:

- The body replaces the whole config rather than merging into it: any group or field you leave out is reset to its default. To change one setting, send the source's current `config` (from `GET /api/sources`) with that setting changed. On a GraphRAG source, keep `"retriever": "graphrag"` and the top-level `graph` object.
- Invalid values are rejected with `400` (strict validation on write).
- The `kind` field (classic / wiki / graphrag) cannot be changed through this endpoint — converting a source to a [Wiki](/Sources/Wiki-sources) or enabling [GraphRAG](/Sources/GraphRAG) uses dedicated endpoints.
- Editing requires ownership of the source or a team `editor` grant; viewers receive `403`.
