# Context Compression

DocsGPT implements a smart context compression system to manage long conversations effectively. This feature prevents conversations from hitting the LLM's context window limit while preserving critical information and continuity.

## How It Works

The compression system operates on a "summarize and truncate" principle:

1.  **Threshold Check**: Before each request, the system calculates the total token count of the conversation history.
2.  **Trigger**: If the token count exceeds a configured threshold (default: 80% of the model's context limit), compression is triggered. An agent with a [history limit](#per-agent-history-limit) also compresses once the messages since the last summary pass it.
3.  **Summarization**: An LLM (potentially a different, cheaper/faster one) processes the older part of the conversation—including previous summaries, user messages, agent responses, and tool outputs.
4.  **Context Replacement**: The system generates a comprehensive summary of the older history. For subsequent requests, the LLM receives this **Summary + Recent Messages** instead of the full raw history.

### Key Features

*   **Recursive Summarization**: New summaries incorporate previous summaries, ensuring that information from the very beginning of a long chat is not lost.
*   **Tool Call Support**: The compression logic explicitly handles tool calls and their outputs (e.g., file readings, search results), summarizing their results so the agent retains knowledge of what it has already done.
*   **"Needle in a Haystack" Preservation**: The prompts are designed to identify and preserve specific, critical details (like passwords, keys, or specific user instructions) even when compressing large amounts of text.

## Configuration

You can configure the compression behavior in your `.env` file or `docsgpt/core/settings/agents.py`:

| Setting | Default | Description |
| :--- | :--- | :--- |
| `ENABLE_CONVERSATION_COMPRESSION` | `True` | Master switch to enable/disable the feature. |
| `COMPRESSION_THRESHOLD_PERCENTAGE` | `0.8` | The fraction of the context window (0.0 to 1.0) that triggers compression. |
| `COMPRESSION_MODEL_OVERRIDE` | `None` | (Optional) A different model to write the summaries, for example a cheaper one such as `gpt-5.4-mini` while `gpt-5.5` answers. It must be a registered model id (from the [model catalog](https://github.com/arc53/DocsGPT/tree/main/docsgpt/core/models) or a custom model YAML); an unknown id makes compression fail, and the failure is only logged. |
| `COMPRESSION_MAX_HISTORY_POINTS` | `3` | The number of past compression points to keep in the database (older ones are discarded as they are incorporated into newer summaries). |
| `COMPRESSION_RECENT_FIELD_MAX_TOKENS` | `8000` | Cap, in tokens, on each prompt, response and tool result in the messages after the last compression point, which are otherwise kept verbatim. One very large message there can undo the compression. `0` turns the cap off. |
| `COMPRESSION_PROMPT_VERSION` | `v1.0` | Which summarization prompt to use, read from `docsgpt/prompts/compression/<version>.txt`. |

## Per-agent context limit

An agent can be set to use less of the context window than its model allows. Turn on **Context limit** in the agent's **Advanced settings** (for a workflow agent, under **Workflow details** in the builder) and enter the number of tokens, or set `config.context_window_limit` through the [API](/API/agent-api#letting-api-callers-make-changes). Turned off (`null` in the API), the agent uses the model's full window.

It is for agents whose conversations run long, such as a Telegram or Slack bot that keeps one conversation per chat. Without a limit, such a conversation grows to 80% of the model's window before it is compressed, and every message after that sends about that many tokens. With a 32,000-token limit, the same conversation is compressed at about 25,600 tokens.

With a limit set, the agent treats the limit as the model's window for:

*   the compression threshold (`COMPRESSION_THRESHOLD_PERCENTAGE` of the limit),
*   how much conversation history each request carries,
*   how many retrieved documents are sent,
*   how much of an attached file is put in the prompt, and how much of one the agent reads per call,
*   when a turn that calls tools compresses its earlier tool results,
*   when a conversation on the OpenAI Responses API stops chaining onto the transcript the provider stores.

The limit never makes a request fail and never stops the agent calling tools. A message, system prompt or tool result larger than the limit is still sent when the model can take it, with less history and fewer documents around it; a question that fills the limit on its own is sent without documents. Only the model's own threshold makes the agent stop calling tools and answer with what it has. A limit at or above the model's window has no effect, so a smaller model keeps its own window. The limit also applies to scheduled runs, webhook runs, background continuations and resumed tool approvals, and to every node of a workflow agent (a node on a smaller model uses that model's window).

Values start at 16,000 tokens. Below that, the system prompt, the tool definitions and a compression summary alone would reach the threshold, and the agent would compress on every turn. The highest value is 10,000,000 tokens, but a limit above the model's window has no effect. The form notes such a limit under the field without refusing it, measured against the largest context window among the agent's models (the instance's default model when none is picked; for a workflow, the models its agent nodes use). Like the agent's usage limits, changing it needs permission to edit the agent's policy, which owners and editors have.

## Per-agent history limit

A context limit lowers the point at which a conversation is compressed, but a long conversation still sits just below that point on most turns: it fills up to 80% of the limit, is compressed, and fills up again. A **history limit** keeps a long conversation small all the time. Turn on **History limit** in the same **Advanced settings** (or **Workflow details**), or set `config.history_token_limit` through the API.

Once the messages sent word for word since the last summary pass the limit, the older ones are summarized and the newest ones are kept, up to half the limit. When the conversation reaches the context threshold at the same time, the context limit wins and every message, the latest included, is summarized. The next request then carries the summary plus the latest exchange instead of the whole thread. With an 8,000-token history limit, each request carries a summary and between about 4,000 and 8,000 tokens of recent messages, whatever the context limit.

*   The summary does not count toward the limit; it is kept to about 4,000 tokens.
*   The history limit runs before each message. The context limit and the model's window still apply as before, for example when tool results fill the context during an answer.
*   A caller that sends its own `history` instead of a conversation id has nothing to summarize into, so that history is trimmed to the limit, oldest messages first. A trimmed history does not chain onto the provider's stored conversation (`previous_response_id` in OpenAI store mode), which still holds the trimmed messages.
*   Each compression adds a summary entry to the conversation and costs one call to the summarizing model, so a low limit means more of both. `COMPRESSION_MODEL_OVERRIDE` can point the summaries at a cheaper model.

Values start at 4,000 tokens and must stay below the context limit. A history limit at or above the model's window has no effect, because the conversation is compressed near the window first; the form notes it under the field. Turned off, the conversation is compressed only near the context limit. Changing it needs the same permission as the context limit.

## Architecture

The system is modularized into several components in `docsgpt/api/answer/services/compression/`:

*   **`CompressionOrchestrator`** (`orchestrator.py`): Entry point. Checks the threshold before each request, and also during a tool loop, when tool results fill the context mid-answer; then it runs the compression and hands back the rebuilt context.
*   **`CompressionThresholdChecker`** (`threshold_checker.py`): Calculates token usage and decides when to compress.
*   **`TokenCounter`** (`token_counter.py`): Counts the tokens of a conversation or message list, including an estimate for attached images.
*   **`CompressionService`** (`service.py`): Runs the summarization, manages DB updates, and reconstructs the context (Summary + Recent Messages) for the LLM.
*   **`MessageBuilder`** (`message_builder.py`): Builds the message list from a summary and the recent messages, including after a mid-loop compression so tool execution can continue.
*   **`CompressionPromptBuilder`** (`prompt_builder.py`): Constructs the specific prompts used to instruct the LLM to summarize the conversation effectively.
