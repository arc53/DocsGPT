# Background Jobs and Data Retention

Besides the API and the worker, DocsGPT needs a **Celery beat scheduler**. Beat puts periodic tasks on the queue, and the worker runs them: source syncs, scheduled agent runs, the reconciliation of stuck work, and the cleanups that keep Postgres from growing without bound. Without beat none of this happens, and nothing tells you so.

## Running beat

At least one beat scheduler must run. Beat uses RedBeat, which keeps its schedule and a lock in Redis, so only the instance holding the lock schedules anything. Starting beat in more than one worker is therefore safe: the extra instances wait and take over if the lock holder stops.

| Install | How beat runs |
| --- | --- |
| `docsgpt up` and the one-line installer | Embedded in the `worker` container (`celery ... worker -B`). Nothing to do. |
| `docsgpt up --native`, `docsgpt worker` | Embedded (`-B`) by default. `docsgpt worker --no-beat` leaves it out; then run `docsgpt beat` as its own process. |
| Checkout Compose files (`docker-compose.yaml`, `docker-compose-hub.yaml`, `docker-compose-standalone.yaml`) | Embedded in the `worker` service with `-B`. |
| Kubernetes manifests | Embedded in `docsgpt-worker` with `-B`, safe on every replica. |
| Development | `celery -A docsgpt.app.celery worker -l INFO -B`, or `docsgpt worker`. See [Development Environment](/Deploying/Development-Environment). |
| Windows | The worker can't embed beat. Run `docsgpt beat` (or `celery -A docsgpt.app.celery beat -l INFO`) in a separate process. |

If you write your own worker command, keep `-B` on it or run `celery -A docsgpt.app.celery beat -l INFO` next to it. Signs that beat isn't running:

- Scheduled agent runs and source syncs never fire.
- A request stuck after a crash is never marked failed.
- In [Activity](/Using/activity), **Now** shows items under **Up next** as **Overdue**, and the **Calendar** marks the times schedules should have run as **Missed**.
- Coming knowledge syncs disappear from the **Calendar**: their next time is already in the past.

## Periodic tasks

Beat schedules these tasks. Each runs on the worker, so the worker must also be running and consuming the `docsgpt` queue, and for `analytics-sweep` and `analytics-gap-digest` the [`analytics` queue](#the-analytics-queue). The cleanups skip themselves when `POSTGRES_URI` is not set.

| Task | Every | What it does | Controlled by |
| --- | --- | --- | --- |
| `schedule-syncs-daily` | day | Re-ingests sources whose sync frequency is **Daily**. | The source's **Sync** setting in Knowledge. |
| `schedule-syncs-weekly` | week | The same for **Weekly** sources. | The source's **Sync** setting. |
| `schedule-syncs-monthly` | 30 days | The same for **Monthly** sources. | The source's **Sync** setting. |
| `dispatch-scheduled-runs` | 30 s | Queues [scheduled agent runs](/Agents/schedules) that are due. | `SCHEDULE_DISPATCHER_INTERVAL` (`30`, minimum 15 s). |
| `cleanup-schedule-runs` | day | Deletes scheduled-run records and their output older than the retention window, keeping the 50 most recent runs of each schedule. | `SCHEDULE_RUN_OUTPUT_RETENTION_DAYS` (`90`). |
| `reconciliation` | 30 s | Marks stuck work as failed and logs an alert: answers that stopped streaming, tool calls left mid-way, stalled ingests, stuck idempotency claims and scheduled runs. | None. |
| `cleanup-pending-tool-state` | 60 s | Deletes paused conversations waiting for a tool approval or a client-side tool result once they expire (30 minutes), and clears their approval prompts. | None. |
| `cleanup-idempotency-dedup` | hour | Deletes idempotency keys for uploads, tasks and webhooks older than 24 hours. | None. |
| `cleanup-message-events` | day | Deletes the per-chunk stream journal that lets a client reconnect to an answer, and the markers left by regenerated answers. Conversations themselves are kept. | `MESSAGE_EVENTS_RETENTION_DAYS` (`14`). |
| `cleanup-guardrail-events` | day | Deletes [guardrail](/Agents/guardrails) events. | `GUARDRAILS_EVENTS_RETENTION_DAYS` (`30`). |
| `cleanup-content-scores` | day | Deletes cached [prompt-injection scores](/Agents/guardrails#where-a-documents-score-comes-from) whose text was not scored or seen within the retention window. | `GUARDRAILS_CONTENT_SCORES_RETENTION_DAYS` (`180`). |
| `cleanup-decision-usage` | day | Deletes the per-day counts of [decision model](/Models/decision-model) calls. | `DECISION_USAGE_RETENTION_DAYS` (`90`). |
| `analytics-sweep` | 5 min | Labels new and changed conversations for [Insights](/Using/analytics-and-logs#conversation-insights), newest first, for up to 4 minutes. Scheduled only while `DECISION_ANALYTICS_ENABLED` is on, read when beat starts. Runs on the `analytics` queue. | `ANALYTICS_SWEEP_SECONDS` (`300`), `ANALYTICS_SWEEP_BUDGET_SECONDS` (`240`). |
| `cleanup-conversation-labels` | day | Deletes conversation labels older than the retention window, by message time. Labels are also deleted with their conversation. | `ANALYTICS_RETENTION_DAYS` (`90`). |
| `analytics-gap-digest` | week | Sends the [weekly docs-gap summary](/Using/analytics-and-logs#weekly-docs-gap-summary) to the owners of agents that turned it on. Scheduled only while `DECISION_ANALYTICS_ENABLED` is on. Runs on the `analytics` queue. | The agent's **Weekly docs-gap summary**. |
| `cleanup-traces` | day | Deletes request traces (the trace viewer and per-agent logs). | `TRACES_RETENTION_DAYS` (`30`). |
| `cleanup-orphan-memories` | day | Deletes memory entries whose tool was deleted. | None. |
| `reap-sandbox-sessions` | 60 s | Closes [sandbox](/Deploying/Sandbox) sessions in the worker that have been idle longer than their keep-alive time. | `SANDBOX_MAX_TTL` (`1200`) caps the keep-alive. |
| `reap-stale-workflow-runs` | 5 min | Marks workflow runs still `running` after a disconnect or crash as failed. | `WORKFLOW_RUN_STALE_SECONDS` (`3600`). |
| `version-check` | 7 hours | Checks gptcloud.arc53.com for security advisories for your version and logs any it finds. | `VERSION_CHECK` (`true`); set `false` to turn it off. |

All the settings above are listed in the [Settings Reference](/Deploying/Settings-Reference).

## The analytics queue

The analytics sweep spends most of its time waiting for the [decision model](/Models/decision-model#conversation-analytics), up to a few minutes per run, so it has a queue of its own, `analytics` (`ANALYTICS_QUEUE`). The worker only reads messages, builds the model's input and writes labels; it never loads the model. The sweep holds a lock in Redis, so overlapping runs and several workers are safe.

- **A bare prefork worker** (`celery ... worker` with no `-Q`, or `docsgpt worker` on Linux) consumes every queue, `analytics` included. While a backlog is being labelled, one of its processes is busy with the sweep and the others take ingestion and query embedding.
- **A solo-pool worker must not consume it.** The solo pool runs one task at a time, so a sweep would hold the whole worker and searches would time out waiting for their query embedding. On macOS and Windows, `docsgpt worker` runs the solo pool and leaves `analytics` out; `docsgpt worker --analytics` takes it in a second process. `docsgpt up --native` installs both; `docsgpt dev` starts the second only while `DECISION_ANALYTICS_ENABLED` is on, read when it starts. With raw Celery and `--pool=solo`, add `-X analytics` and run `celery -A docsgpt.app.celery worker -l INFO -Q analytics -n analytics@%h --pool=solo` next to it; `-n` gives it a node name of its own on the shared host.
- **The shipped Compose files and Kubernetes manifest** list it: `-Q docsgpt,parsing,embeddings,ingest,analytics`.
- **On a single-CPU host** a prefork worker starts one process (the default concurrency is the CPU count), so with `DECISION_ANALYTICS_ENABLED` on, a sweep holds it for up to `ANALYTICS_SWEEP_BUDGET_SECONDS` plus one call's `DECISION_BACKGROUND_TIMEOUT`, and searches time out waiting for their query embedding. There, run a dedicated `-Q analytics -c 1` worker as below and drop `analytics` from the main worker's `-Q`, or give the main worker `-c 2`. The shipped files leave concurrency at its default, since each process holds its own memory.
- **A worker you start with your own `-Q`** must list `analytics` too, or the sweep never runs and the Insights pages stay at **Analyzing conversations**, with none analyzed. Nothing else depends on it.

Beat schedules the sweep and the digest only while `DECISION_ANALYTICS_ENABLED` is on, so the queue gets no messages otherwise; restart beat (the worker that embeds it) after turning the switch on or off. A message no worker takes stays in Redis until one does, which then drops it if its interval has passed.

`docsgpt doctor` reads that backlog from the broker while `DECISION_ANALYTICS_ENABLED` is on. Three or more messages waiting is a warning that names the fix, `docsgpt worker --analytics` next to the worker or `analytics` in its `-Q`, along with the workers that answer a one-second ping and consume the queue. A worker busy with a sweep may not answer, and doctor run before any worker starts sees at most a message or two, so neither is reported as a problem.

To keep the sweep apart from the rest, run one worker for it alone and leave `analytics` out of the others:

```bash
celery -A docsgpt.app.celery worker -l INFO -Q analytics -c 1 -n analytics@%h
```

One process is enough: only one sweep runs at a time. `-n` keeps its node name apart from a worker on the same host.

### Labelling past conversations

When labelling is turned on, the sweep labels the last `ANALYTICS_BACKFILL_DAYS` (7) days, newest first, within its time budget. To label further back, or all at once, run the same sweep in the foreground with no time budget:

```bash
docsgpt analytics backfill --days 30 --dry-run   # the unlabelled messages, turns and an estimated time; labels nothing
docsgpt analytics backfill --days 30             # label them; --agent <id> limits it to one agent
```

Run it where a worker runs, with the worker's settings: in a Docker stack, `docker compose exec worker python -m docsgpt analytics backfill --days 30` from the stack's folder; in Kubernetes, `kubectl exec deploy/docsgpt-worker -- python -m docsgpt analytics backfill --days 30`. Its model calls go where the worker's go, at background priority, so chat still comes first. `--days` can't exceed `ANALYTICS_RETENTION_DAYS`, since older labels would be deleted and made again. `--dry-run` counts the messages that have no labels from the model a real run would use; with a decision server (`DECISION_MODE=api`) it first asks the server which model it runs, and if the server does not answer, or `DECISION_BASE_URL` is not set, the output carries a `warning` that the counts assume the default model. The estimate in `--dry-run` comes from this server's measured speed, and is `null` until the model has been timed; the wall time is longer than the compute time, since background work takes at most a quarter of the cores. The command does nothing while `DECISION_ANALYTICS_ENABLED` is off. While a scheduled sweep is running it says so and waits for it to finish, for up to one sweep's length (`ANALYTICS_SWEEP_BUDGET_SECONDS` plus `DECISION_BACKGROUND_TIMEOUT` plus a minute); `--no-wait` exits with `{"skipped": "locked"}` instead. `--agent` takes an agent's id.

## Kept until deleted

No task trims the following. They grow for as long as the instance runs, and they are removed only when a user, an admin or you delete them:

- **Conversations and their messages.** Users delete them one by one or all at once in the web app.
- **Token usage** (`token_usage`). Quotas and analytics read it.
- **Request logs** (`stack_logs`, `user_logs`). The Logs pages and analytics read `stack_logs`.
- **The audit logs**: `auth_events` (sign-ins, access and configuration changes) and `device_audit_log` (remote-device commands).
- **Tool call records** (`tool_call_attempts`) and **workflow runs** (`workflow_runs`).
- **Sources, attachments and artifacts**, including their files in storage and their vectors.
- **Agents, prompts, tools, memories, notes and todos.**

<Callout type="info">
  If you need a retention limit on any of these, for example for GDPR, delete old rows yourself on a schedule, such as `DELETE FROM stack_logs WHERE timestamp < now() - interval '180 days'`. Back up the database first, and keep `token_usage` as long as your quota periods need it.
</Callout>
